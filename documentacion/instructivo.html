El mapa de dependencias

Lo que hay que entender antes de tocar nada: qué necesita qué. Las flechas se leen «alimenta a».

data_dsmarket/ (los 3 CSV originales) │ ▼ lakehouse/ bronze → silver → gold pipeline.py │ ├──────────────► notebooks 01 · 02 EDA y clustering │ │ │ ▼ │ clusters_*.csv ──► vuelve al gold │ ├──────────────► notebook 03 forecasting │ │ │ ▼ │ cache_forecast/ predicciones y p90 │ │ │ ┌─────────────┼──────────────┐ │ ▼ ▼ ▼ │ notebook 04 notebook 05 carga_predicciones.py │ abastecimiento elasticidad │ │ ▼ └──────────────────────────────────► gold/fact_predicciones gold/fact_reposicion │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ api/ app/ PowerBI

De dónde salen los grupos. El gold lee cache_forecast/segmentacion_productos.csv y cache_forecast/tienda_mas_parecida.csv, que escribe el propio notebook 02. Si reejecutás el clustering, basta con regenerar el gold (paso 4) para que el resto del sistema use los grupos nuevos.

Primera vez

Ocho pasos. Los tres primeros son obligatorios; del cuarto en adelante cada uno produce un entregable independiente.

01

Entorno

~5 min

Python 3.11 o 3.12. Evitá 3.13 y 3.14: son demasiado recientes y varios paquetes del proyecto todavía no tienen rueda compilada para ellas — Prophet el primero. Conviene un entorno virtual para no mezclar con lo que ya tengas instalado.

# desde PROYECTO/
python3 -m venv .venv
source .venv/bin/activate          # en Windows: .venv\Scripts\activate

pip install pandas numpy scipy scikit-learn matplotlib seaborn \
            duckdb lightgbm xgboost statsmodels prophet \
            jupyter nbformat nbclient ipykernel \
            fastapi "uvicorn[standard]" streamlit altair

Prophet es el que más tarda porque compila su motor de inferencia. Si falla, el resto del proyecto funciona igual: solo se pierde una de las cinco familias de modelos comparadas en el notebook 03.

En macOS hace falta un paso más. LightGBM y XGBoost usan OpenMP y macOS no lo trae. Sin esto, el import lightgbm falla con Library not loaded: @rpath/libomp.dylib y el notebook 03 no arranca.

brew install libomp

# comprobar que quedó donde LightGBM lo busca
ls -l /opt/homebrew/opt/libomp/lib/libomp.dylib
python3 -c "import lightgbm, xgboost; print(lightgbm.__version__, xgboost.__version__)"

Después de brew install libomp hay que reiniciar el kernel del notebook: no hace falta reinstalar LightGBM, el binario ya estaba bien.

Si no tenés Homebrew, instalalo primero — y ejecutá las líneas que imprime bajo «Next steps», porque sin ellas brew sigue sin existir como comando:

xcode-select --install
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# en Apple Silicon, lo que imprime al final suele ser esto
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
eval "$(/opt/homebrew/bin/brew shellenv)"

La alternativa sin Homebrew, que además resuelve la versión de Python. conda-forge trae llvm-openmp como dependencia de LightGBM y XGBoost, así que no hace falta libomp del sistema — y de paso fija Python 3.12 y evita compilar Prophet, que es donde más gente se atasca.

curl -L -O "https://github.com/conda-forge/miniforge/releases/latest/download/Miniforge3-$(uname)-$(uname -m).sh"
bash "Miniforge3-$(uname)-$(uname -m).sh"
# cerrar y reabrir la terminal

conda create -n dsmarket python=3.12
conda activate dsmarket
conda install -c conda-forge lightgbm xgboost duckdb pandas numpy scipy \
    scikit-learn matplotlib seaborn statsmodels jupyter altair prophet
pip install streamlit fastapi "uvicorn[standard]"

Con este camino, en Jupyter hay que elegir el kernel dsmarket en vez del de .venv.

02

Verificar los datos de origen

10 s

Los tres CSV tienen que estar descomprimidos en su sitio. Si solo tenés el .zip, descomprimilo primero.

ls -la data_dsmarket/data_dsmarket/

03

Construir el lakehouse

~40 s

Las tres capas de una vez. Es el paso del que depende todo lo demás.

python3 lakehouse/scripts/pipeline.py all
BRONZE — ingesta sin transformación item_sales 30.490 filas 20,9 MB item_prices 6.965.706 filas 1,2 MB SILVER — limpieza y normalización ventas (formato largo) 58.327.370 filas 30,8 MB control de calidad: ventas>0 sin precio = 0 GOLD — modelo dimensional fact_ventas 58.327.370 filas 83,5 MB

El número que hay que mirar es el control de calidad: tiene que dar cero. Si no da cero, el alineado de precios se rompió y todo lo que venga después estará mal.

04

Notebooks 01 y 02 · EDA y clustering

~2 min

Se abren y se ejecutan de arriba abajo. Producen los hallazgos descriptivos, los grupos de producto y la tienda más parecida a cada una.

jupyter notebook 01_EDA_DSMarket.ipynb
jupyter notebook 02_Clustering_DSMarket.ipynb

El notebook 02 deja en cache_forecast/ los dos CSV que consume el gold: segmentacion_productos.csv (grupo de cada producto) y tienda_mas_parecida.csv. Si cambiás algo del clustering, basta con reejecutarlo y regenerar el gold:

# desde la terminal:
python3 lakehouse/scripts/pipeline.py gold
05

Notebook 03 · Forecasting

15 s o 20 min

Este es el que tiene truco. Si la carpeta cache_forecast/ está poblada, el notebook carga los modelos ya entrenados y corre en 15 segundos. Si la borrás, reentrena todo desde cero: unos 20 minutos.

jupyter notebook 03_Forecasting_DSMarket.ipynb

# para forzar el reentrenamiento completo:
# mv cache_forecast cache_forecast_viejo

La caché no es una trampa: es el patrón normal de un proyecto con modelos caros. Está declarado en el propio notebook y el código de entrenamiento está a la vista.

06

Notebooks 04 y 05 · Abastecimiento y elasticidad

~1 min

Ambos leen del lakehouse y de la caché de predicciones. No entrenan nada: el 04 es simulación vectorizada y el 05 son regresiones con efectos fijos.

jupyter notebook 04_Abastecimiento_DSMarket.ipynb   # ~10 s
jupyter notebook 05_Elasticidad_DSMarket.ipynb     # ~31 s

El 04 escribe además los dos CSV de entrega: predicciones_28dias.csv y predicciones_28dias_p90.csv.

07

Cerrar el círculo: predicciones al almacén

~5 s

Vuelca las salidas de los modelos al gold como tablas de hechos. Sin este paso, la API, el panel y PowerBI no ven las predicciones.

python3 lakehouse/scripts/carga_predicciones.py
predicciones de 2016-04-25 a 2016-05-22 para 30.490 series fact_predicciones 853.720 filas 5,4 MB fact_reposicion 121.960 filas 0,5 MB
08

API y panel

~30 s

Son dos procesos independientes: el panel no necesita que la API esté levantada, porque lee el lakehouse directamente y aplica la misma política.

# comprobar que la API responde bien (12 pruebas)
python3 api/test_api.py

# levantarla · documentación navegable en /docs
uvicorn api.main:app --reload

# en otra terminal, el panel · abre en :8501
streamlit run app/inicio.py

Para activar la capa de lenguaje natural del panel, antes de arrancarlo:

pip install anthropic
export ANTHROPIC_API_KEY="tu-clave"

Sin clave, el panel funciona completo con las explicaciones por reglas. Solo se desactiva la pestaña de consultas.

La forma corta: un solo comando

Desde que existe operacion/, todo lo de arriba se puede lanzar de una vez. Los pasos manuales siguen valiendo y sirven para entender qué pasa; esto es lo que se usa el día a día.

python3 operacion/orquestador.py              # las nueve etapas, en orden
python3 operacion/orquestador.py --simular    # el plan, sin ejecutar nada
python3 operacion/orquestador.py --estado     # qué pasó en las últimas ejecuciones
python3 operacion/orquestador.py --desde predecir   # reanudar donde falló

Las etapas son: bronce → plata → oro → contratos → entrenar → predecir → reposicion → contratos → monitor. Se detiene ante el primer fallo bloqueante y no publica nada. Los contratos corren dos veces a propósito: la segunda pasada es la que impide que un modelo roto llegue a la API.

ComandoQué haceTarda
operacion/contratos.py --detalleLos 13 contratos de datos, uno por uno~30 s
operacion/entrenar.pyLos 8 modelos y su alta en dim_modelo~20 min
operacion/predecir.pyCarga los modelos y predice 28 días~3 min
operacion/reposicion.pyNiveles objetivo por serie~10 s
operacion/monitor.pyError realizado, deriva y umbrales~1 min
operacion/modelos.pyLista los modelos registrados1 s

Si te quedás sin memoria. El límite de DuckDB se ajusta por variable de entorno: export DSMARKET_MEM=8GB en un equipo holgado, 1GB en uno justo. DuckDB vuelca a disco cuando lo necesita, así que un límite bajo cuesta tiempo, no errores.

Para que corra solo, una entrada de cron semanal basta a esta escala:

0 3 * * 1  cd /ruta/PROYECTO && /usr/bin/python3 operacion/orquestador.py >> operacion/registro.log 2>&1

Si tuvieras que dejar el proyecto y retomarlo en un mes, ahora es un solo comando: python3 operacion/orquestador.py. Reconstruye el almacén, comprueba los contratos, reentrena, predice, calcula los niveles objetivo y te dice si algo se está degradando. Y si falla, --estado te cuenta en qué etapa y por qué.
